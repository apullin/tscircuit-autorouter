## 1. Critical finding: A2 worker pool result-crossover (HIGH, confirmed by code path)

`lib/parallel/a2Pool.ts:56-99` + `a2BranchWorker.ts:37-56` (stack + r3 identical):
`runA2Branches` throws on the first branch error and abandons the sibling worker
mid-computation — no drain, no poison, no `busy` check on next dispatch (the flag is
written but never consulted). In persistent benchmark workers
(`scripts/benchmark/benchmark.worker.ts`, `.child.ts`) the NEXT board reuses the pool and
can consume the PREVIOUS board's late-arriving routes as its own "broad" result — silently
wrong output or a torn-read crash. Trigger: any branch failure mid-batch with
`TS_PARALLEL_A2=1`. **Fix before A2 is ever enabled for real runs**: on error, terminate +
respawn workers (or drain via generation stamps in the SAB header), add a Worker `error`
listener and a pump timeout (currently an unbounded `while` + `sleepSync(1)` — a worker
that fails at module load hangs the pipeline forever). Two lesser A2 notes: JSON round-trip
normalizes NaN/±Inf/−0; 64MB SAB is a board-size cliff (worker writes overflow-error).

## 3. Unrecorded results (exist only in exp/rewrites commit messages)

- **TS_PARALLEL_HD_NODES (f354b3c2) WORKS and is the biggest unbanked win**: node-level
  parallelism across the ~1200 independent HD nodes (shared context broadcast once,
  Atomics.wait pump, A2-style SAB channels). Measured: sample 8 133→91s @4 workers
  (1.46x), sample 6 344→189s (1.82x — at the measured board-level ceiling), **DRC
  identical at every worker count** (31/98). Ceiling analysis: saturates at 4-8 workers;
  stragglers 12.2s/62.5s. Off by default, absent from WINS.md.
- **A quality-affecting default change is hidden inside that same commit**: growth ladder
  `GROWTH_SCHEDULE="1.2,2,4,8"` (default ON at exp/rewrites HEAD) moved sequential
  baselines s8 123s/45 DRC → 133s/31, s6 268/99 → 344/98. Needs to be split out and gated
  on the full corpus as its own experiment (1.2-only variant was catastrophic on s6:
  99→289 DRC).
- **Two proven upstream design defects** (f618a974, direct-geometry attribution, 55
  violations on s8, 0 unattributed):
  (a) **cross-node clearance margin too small by construction** — per-node margin
  obstacleMargin/2=0.075mm ⇒ adjacent nodes can pack traces 0.15mm apart < 0.2mm required;
  69% of violations are cross-node pairs.
  (b) **growth is a DRC-violating relaxation** — `scaleRoute()` scales coordinates but not
  traceThickness/viaDiameter, so 2x-scale solves return 0mm gaps; grown nodes are 1% of
  the mesh but carry 47% of intra-node violations (~48x enrichment).
- **Doomed nodes are over-committed, not unroutable** (270ca10e/16da17b0): 40/40 captured
  failing-node instances become routable by removing any one of ~77% of single
  connections. The 68-88% of HD search burned on them is the cost of discovering they
  need a larger scale; caps don't help (measured), salvage-before-grow is worse (measured:
  a complete-but-slightly-illegal routing repairs better than an incomplete legal one).
  ⇒ the credible fix for sample 6 + the DRC tail is **eviction + re-path at the
  assignment level** (move one net to a neighbor node), not more search.
- **Wavefront/negotiated-congestion prototype** (461e5fb8): mechanically complete
  PathFinder-style global router; 0 unroutable after 3 bring-up fixes, but 3x the trace
  length of the pipeline and 1854 vs 0 DRC on sample 5 — not competitive; weeks of work
  to close. It IS the one GPU-shaped algorithm in the codebase (single cost field, one
  kernel for all nets) if ever revived.
- **maxInnerIterationsPerGrowthAttempt was a silent no-op** — found, fixed, tested on
  bugfix/growth-attempt-iteration-cap (2e74a497, based on v0.0.717, zero default blast
  radius confirmed by review). Ready-now upstream PR.

## 5. Recovered round-5 analysis: tiny-hypergraph / portPointPathing (21.7% of s8 wall)

(The original dispatch died on a 400 prompt-too-long on 2026-07-26 14:53; redone today.)
Stage = one SelectiveRerip A* (IndexedCandidateHeap binary heap, numeric hopIds — string-key
win NOT available). Stage-internal: computeG family 53%, selective-rerip blocker search
28%, heap ~10%, dequeue 7%. Ranked, with the key structural insight that **every port has
exactly 2 incident regions ⇒ hop space is 2·portCount, not portCount·regionCount**:

- **R1 (M, identity-SAFE, ~2-4% of wall)**: compact hopId = portId*2+side ⇒ replace the
  sparse-mode Maps (candidateBestCostByHopId, heap indexByHopId Map + closedHopIds Set)
  with typed arrays + generation stamps. Kills 2 Map.get/dominance check, 2 Map.set/admit,
  Map.set per sift level.
- **R2 (S then M, safe)**: hoist the dominance check above the per-neighbor candidate
  object literal (currently allocates then discards dominated candidates, core.ts:598-614);
  then SoA candidate pool (proven pattern). R1+R2 together ≈ one "expansion-core rewrite",
  ~3.5-6% of s8 wall, ~2.5-4.5% of s6.
- **R3 (M, safe)**: hoist per-dequeued-candidate invariants across the neighbor loop
  (regionCache fields, port angle, z, congestion, `viaSizeWithMarginSq` rebuilt per call in
  computeRegionCost.ts:46-47). ~2-3.5% wall.
- **R4 (S)**: packed-int return from countNewIntersectionsWithValues (tuple alloc/call).
- **R5/R6 (M/S)**: blocker-search churn — getPortOwners() rebuilt twice per failure with
  unchanged state (selective-rerip :196/:231→:334); owner Sets → insertion-ordered arrays
  + bitset (CAUTION: `[...owners]` order feeds rip order — bare bitset is NOT identity-safe).
- Flags: dead goal branch core.ts:608-611; heap replace-test uses `g` while ordering uses
  `f` (consistent only because goal-hops have h=0 — deserves a comment).

## 7. Forward roadmap (recommended order)

**Hours — consolidation (highest value/effort ratio in the whole project):**
fix A2 pool (§1) → restore perf-patches/ onto the stack + add math-utils as a real
patchedDependency → push stack tip + WINS delta → apply-or-decide the hypot patch →
open the 3 upstream PRs (§4, respecting the branch hazard) → file the upstream issues →
rebase stack onto v0.0.718 (one trivial hunk).

**Days — measured TS wins:** tiny-hypergraph R1+R2 (+R3/R4/R6) ≈ 6-10% of wall,
identity-safe; trace-simplification shared flatbush (kill the O(routes²) term properly —
round-4's bbox reject was the 80/20); growth-ladder as its own corpus-gated experiment;
HD-node parallelism productization (CLI/server contexts; browser keeps sequential).

**The algorithmic lever (sample 6 + the DRC tail):** eviction + re-path of over-committed
nodes. Everything points at it: 77% drop-one rescue rate, 62.5s straggler node bounding
the parallel ceiling, 69% cross-node + 48x grown-node violation enrichment. This is the
one item that improves speed AND quality AND the parallel ceiling simultaneously.

**Rust (the honest scope):** kernel ports are a proven wash (native A01: bit-identical,
1.65x kernel, wash overall — typed-array TS is within 1.5-3x of native). The winning shape
is **the HD-stage portfolio on Rust threads with shared memory**: P2-replay winner
semantics are already cracked (549/550 exact), and the only things that killed JS-side
parallel portfolio were worker transport cost and the failure-cache identity wrinkle —
threads + shared memory erase the first, and a per-thread cache policy addresses the
second. Scope: port the SingleHighDensityRouteSolver family + supervisor schedule as a
cdylib (bun:ffi), rayon-style candidate execution, replay-schedule selection. Weeks, not
days; potential further ~2-4x on the HD stage beyond node-level parallelism, and it
directly answers the Tenstorrent question for free.

**CUDA:** stays parked (kernel-inventory.md conclusion re-endorsed after review). Explicit
re-entry triggers: (a) parallel candidate scoring multiplies DRC-eval counts back up
(cuSpatial pairwise_linestring_distance is drop-in shaped), (b) a wavefront-class global
router is ever revived (the one GPU-shaped algorithm here), (c) SoA SegmentTable (C1)
exists and profiling shows a batched geometry residual ≥10% again.

**Tenstorrent n300 (other machine):** genuine architectural fit for the portfolio — ~128
MIMD Tensix cores with ~1.5MB SRAM ≈ one intra-node candidate search per core, which is
exactly the shape SIMT GPUs are bad at. But tt-metal bring-up is a research project, and
the strategic question it answers ("does parallel candidate execution pay?") is being
answered for free on CPU: HD-nodes already says yes at node granularity (1.5-1.8x), and
the Rust-threads experiment answers it at candidate granularity. Recommendation: do it as
a parallel exploratory track only if the fun justifies it — bring up tt-metal remotely,
port ONE candidate solver, measure dispatch economics — but keep it off the critical path.

**Unexplored cheap axis:** all numbers are bun/JSC, but downstream users run Node/V8 and
browsers. One runtime A/B (published dist under node vs bun on samples 5/8) could reshuffle
priorities (JIT behavior on megamorphic solver code differs a lot between engines. The
parallel pools are Bun-API-only and would need a node/web-worker port for users to benefit).
